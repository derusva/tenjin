## 1. 决策内容

### 1.1 作废

《Tenjin Capture Inbox MVP PRD》（`docs/prd/2026-07-12-tenjin-capture-inbox-mvp.md`）的**近期实施范围**作废。逐条去留见该 PRD 文首批注——**按条款继承，不按整章继承**。

作废理由：该 PRD 的核心前提是「先收下、稍后理解」——用 iOS 分享菜单把文字/链接/截图批量投递到 iCloud，Tenjin 事后集中导入并处理。用户的真实行为与之相反：阅读中遇到卡点当场截图问外部 GPT Coach，即刻获得解释。因此该 PRD 的阶段门槛（阶段 B 的 10 次真实捕获 + 5 条延迟处理、阶段 C 的 50 次捕获 + 20 条延迟处理、第 16 章的完成定义）无法从用户的实际使用中产生数据，继续持有会让它变成一份既不能证实也不能证伪的僵尸计划，并与新方向争夺同一份稀缺资源（用户真实的日语阅读时间）。

### 1.2 采纳方向

**Coach 结构化剪贴板桥**：用户在外部 GPT Coach 会话末说「整理」，Coach 输出固定格式 JSON；Tenjin 提供粘贴导入、逐条预览确认后由本机生成事件。外部模型只能提议，用户确认才成为学习事实。

明确不做（升格为永不做）：后台定时抓取任何外部源；Coach 直连 Tenjin 的常驻推送链路（Custom GPT Action、公网服务端、鉴权队列）；Tenjin 内置视觉或 LLM API；画像自动同步或常驻上传；让导入成为记录的必经路径（无 LLM 的手动闭环必须永远完整可用）。

### 1.3 新增的一等设计约束：双硬门

用户明确指出：他真实的日语接触发生在三件他本来就在做的事里——看日文小说、玩日文游戏、刷日文社交内容；他不接受在这三件事之上再叠加一个「学习流程」。

这条约束的地位等同于 `HANDOFF.md` 的既有硬约束（不制造欠账、采集轻、最少维护），但**它不是"时间优先于学习效果"**。正确形式是两道硬门，必须同时成立才保留功能：

- **门① 时间受控**：额外 Tenjin 时间必须有明确预算。默认每周额外不超过**约 6 分钟**（不含他本来就在做的阅读与问 Coach）。随时可退出，不要求清空任何列表，不显示欠账或积压。
- **门② 价值可见**：在该预算内仍看不到回忆或迁移价值，就删除功能。**不能为了省时间而保留一个根本无效的工具。**

推论规则：任何增加单条目人工成本或复习次数的设计，必须先证明它在门①下仍成立；任何为省时间而削弱验证强度的设计，必须先证明它不会让门②失效。

### 1.4 关于用户的三个渠道（措辞受限）

**可以声称的**：在当前证据与维护预算下，唯一被真实行为验证、且能以低维护同时覆盖这三类场景的共同路径是「截图 → Coach」。

**不可声称的**：不说它是技术上唯一可能的路径——社交内容确有 API；小说若在支持选词复制的阅读器里也能直接取文本。这里成立的只是"在当前证据与维护预算下唯一成立的共同路径"，而不是"技术上唯一"。

**不可声称的**：不说"这三个渠道全部是阅读"。当前拟接入的卡点以阅读为主，因此 v1 先做 R；但游戏与视频同样可能产生听力卡点，只是当前不接。R 优先是范围选择，不是渠道性质的结论。

## 2. 已定的设计决策（供实现参考，细节待设计文档）

### 2.1 契约

`tenjin.coach-transfer/v1`，一批 0–3 条（实际入账目标 1–2 条，允许 0 条），v1 只做 R 项（`type: "lookup"`）。字段：

| JSON 键 | 落库位置 | 说明 |
|---|---|---|
| `focus` | 新增 `ContextRecord.focus`（可选） | 见下方定义。作为 `item_created` 的 `display` / `identityKey` 来源 |
| `sourceExcerpt` | 已有 `ContextRecord.original` | **不新增字段**，`original` 语义保持「采集到的原始文本」不变 |
| `answer` | 已有 `ContextRecord.answer` | 最多一两句 |
| `transferSentence` | 导入台账，**不进 ContextRecord** | 不进 contextHash、不进 identity 比较、不可作晋升证据 |

**`focus` 的定义**：可独立复习的最小完整 chunk；保留决定意义的助词、活用与句法槽位；**能规范化时才规范化，不强制辞书形**。若活用或语气本身就是要学的点（如 `〜ておけばよかった`、`〜てしまう`），保持该形态，不得强行还原成辞书形——强制辞书形会破坏 `explanation-policy.md` §3「chunk 必须保留必要的助词、补语或句法槽位；过度裁剪会造成错误泛化」。

L 通道不接（截图不能证明"没听出"，且现有 L 复习没有可核对锚点，批量导入 L 项会制造"无锚点却能产生验证证据"的题目）。P 通道只接真实的原表达 + 纠正版。

**未知键一律整批拒绝，不再"剥离后继续接收"（2026-08-07 收口）。** 原先写的是"解析层剥离 ★级评分、频率与考级断言、词源理论、掌握程度判断并展示给用户"。这条已作废，理由有二：① 剥离意味着解析器要维护一张**已知坏字段黑名单**，而黑名单永远漏——下一个没见过的字段会被静默放行；② 出现这些字段本身就是**Coach 违反了输出契约**的信号，此时这一批的其余条目也不该被信任。改为：`additionalProperties: false`，任何未知键 → **整批拒绝**，并输出可回贴给 Coach 的重新输出指令。禁止把模型自评置信度当把关手段。

### 2.2 冻结的输出契约

Coach 有两种模式，纪律不同：

**普通模式（日常解释）**：**必须逐句完整翻译**截图/材料里的每一句，不得跳句、不得只挑"重点句"翻。窄 focus 的约束**只作用于附加说明**——即"哪些点值得展开讲"最多 1–3 个，而**不是**"哪些句子值得翻译"。这两件事被混淆过：窄 focus 是 `explanation-policy.md` §2 对**解释广度**的约束，它从来不许可省略原文本身的翻译。省略了句子，用户就无法判断 Coach 是否真的读懂了那一句，也无法发现漏读。

**「整理」模式的执行合同（四条，全部为硬条件）**：

1. 整条回复**恰好一个** fenced code block；
2. **围栏总数必须恰好为 1**——不是"恰好一个 JSON 围栏"，是**一共只能有一个围栏**。正文里再放一个引用日文的围栏也算违反；
3. **围栏之外只允许空白**——不得有前言、后记、解释或"以下是整理结果"之类的过渡句；
4. 无围栏、额外围栏、围栏外有正文、JSON `parse` 失败、schema 校验失败——**任一发生即整批失败**。

第 2、3 条比"只能有一个 JSON 块"更严，是刻意的：只要允许围栏外有正文，就得判断"哪段是正文哪段是数据"，而那正是启发式的入口。一刀切成"围栏外只有空白"，判定就退化成可机械执行的检查。

**冻结的 schema**（两层都 `additionalProperties: false`）：

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "additionalProperties": false,
  "required": ["schema", "items"],
  "properties": {
    "schema": { "const": "tenjin.coach-transfer/v1" },
    "items": {
      "type": "array",
      "maxItems": 3,
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["type", "focus", "sourceExcerpt", "answer"],
        "properties": {
          "type": { "const": "lookup" },
          "focus": { "type": "string", "minLength": 1 },
          "sourceExcerpt": { "type": "string", "minLength": 1 },
          "answer": { "type": "string", "minLength": 1 },
          "transferSentence": { "type": "string", "minLength": 1 }
        }
      }
    }
  }
}
```

`items` 允许为空数组（这一批没有值得复习的内容），这是**正常输出**不是失败。

**字符串一律"trim 后非空"，`minLength: 1` 不够。** JSON Schema 的 `minLength: 1` 只挡空串，`" "`、`"\n"`、全角空格都能过。这些值进了账就是一条无法复习、也无法解释的空条目。因此解析层在 schema 之外**再做一次 trim 非空校验**（`value.trim().length > 0`），任一字段不满足即整批拒绝。

**字段分层（不可混淆）：**

| 来源 | `focus` |
|---|---|
| **Coach transfer**（本契约） | **必填**。Coach 的整个价值就是替用户定位那个 chunk；缺了它这条记录退化成"整句 + 一段解释"，正是要摆脱的形态 |
| **legacy / 手工录入的 `ContextRecord`** | **允许缺省**，缺省时从 `original` 派生（即现状） |

写下这条是因为两者容易被一句"`focus` 可选"糊在一起：契约层必填、存储层可选，两件事。

### 2.3 结构错误与语义错误分开处置

两类错误的把关点**不同**，混为一谈会导致对 parser 能力的错误预期：

| 类别 | 例子 | 谁拦 | 后果 |
|---|---|---|---|
| **结构错误** | 围栏数不对、围栏外有正文、JSON parse 失败、未知键、缺必填、类型错、`schema` 值不符、字符串 trim 后为空 | **parser** | **整批拒绝** |
| **语义错误** | `answer` 是编造的、`focus` 圈错了 chunk、`sourceExcerpt` 与截图不符 | **用户在预览时** | 该条**不入账**，记一次 prompt 缺陷 |

**必须删除的错误表述：** 曾经写过（或可能被读成）"编造的 `answer` 会被 `additionalProperties` 拒绝"——**这是错的**。`additionalProperties: false` 只拦**未知键**，对一个键名合法、值是胡说八道的 `answer` **完全无感**。编造内容是语义问题，只有人能判。把它算进 parser 的能力范围，会让人以为"schema 过了 = 内容可信"，而那正好是这条路线最危险的误解。

### 2.4 解析策略（已确认）

1. 提取：见 §3.2。整条回复必须满足 §2.2 的四条执行合同。
2. 严格 schema 校验 + trim 非空校验：任一不合规**整批拒绝**。
3. **不做智能修复、不猜字段、不剥离未知键。**
4. 任一条件不满足即整批失败，并给出一段可回贴给 Coach 的重新输出指令。（原先这里还有一条"多个候选块或提取歧义时失败"——§2.2 的"围栏总数恰好为 1"已经把它吞并了，消歧场景不再存在。）

### 2.5 必须同时满足的实现约束

- `focus` 必须**同时**进入 contextHash 输入与 `contextsHaveSameIdentity` 比较。只进其一必然导致静默丢数据或永久保存失败。
- contextHash 字段清单目前有三处副本，须合并为单点导出并加键集一致性测试；缺省字段继续整键省略，不得发 `null` 或空串（这是历史 hash 不变的唯一保证）。
- `identityKey` 语义域从句级变为 chunk 级，须加命名空间前缀（沿用既有 `image:` 先例）。
- **存储层**的 `focus` 可选、缺省时从 `original` 派生，手动采集路径与导入路径第一天就统一为这一套派生逻辑，不允许长出两类形状不同的 item。注意这与 §2.2 的**契约层必填**不矛盾：Coach transfer 必须给 `focus`（给不出就整批拒绝），而 `ContextRecord` 允许缺省是为了兼容 legacy 与手工录入。两层不同要求，别用一句"`focus` 可选"糊过去。

### 2.6 复习与验证

- 间隔条件**只产生排序优先权，永不产生准入权**。未到期项不被剔除，只排在到期项之后。理由：硬门槛会让"到期集合"成为真实存在但界面不显示的量，即 `HANDOFF.md` 9.1 明文禁止的隐形欠账。
- 探测材料档位在 MVP-A 收敛为两档：`source`（来源句）→ `reduced`（focus 本身）。`transfer` 档仅在采集端显式提供迁移句时启用，未提供的项永远停在 `reduced` 且不受惩罚。
- `transfer` 档一律为**产出式探测**：题面 = focus + 「请自己造一句用到它的句子，或说出它适用什么场合」；生成内容只出现在揭示侧，永不进入被测面。
- 否决「至少一次 transfer 才能晋升 stable」：状态由事件重放派生，部署即让所有既有 stable 静默退回 unstable。替代为不进状态机的派生标记 `transferConfirmed`，仅用于展示与 stable 抽查排序。
- `probeSource` 须枚举化，且**必须保留 `"review"` 作为 legacy 值**，否则恢复等价验证会在校验历史事件时逐条失败。
- 复习默认改为**约 2 分钟的时间预算**（`HANDOFF.md` 9.1 承诺过但从未实现），不再显示"还剩几条"。
- 取消「必须凑满 20 个完整样本」这一指标目标。

### 2.7 完整状态备份必须覆盖什么（取代 REC-02 的字段清单）

**原则**：完整状态备份必须覆盖正式事件、contexts（含图片原始字节）、时钟与水位，以及**所有影响幂等与恢复正确性的 fold 外状态**——包括未来的 Coach 导入台账（import receipts）。

旧 PRD REC-02 列举的具体字段（Inbox 元数据、`sourceShardMonth`、`sourcePackageRelativePath`、`localDigestVersion`、`localPackageDigest`）绑定 Inbox 形态，不继承。继承的是"凡是不能由事件集重算、却影响幂等或恢复的状态，都必须进备份"这条原则。

A1 恢复切片的完整定义另见 [`2026-08-05-a1-ledger-recovery-slice.md`](2026-08-05-a1-ledger-recovery-slice.md)。

### 2.8 已知缺陷与未决项

- **导入幂等只在单设备成立**：导入台账不是事件、不能由事件集重算、不参与 `.tenjin` 交换。恢复到空库后重导同一批会静默重复；同一批 JSON 在两台设备各导一次会产生重复 item。这从设计上打破 `HANDOFF.md` §13.1 的属性「重复导入不增加证据」。处置：台账必须进备份与恢复等价校验（§2.7）；跨设备幂等作为已知缺陷纳入 A2。若 A0 最终决定批次身份进事件层，则台账实现需一次数据迁移。
- **探测材料档位依赖 context 是否存在**：默认导出不带 contexts，而 `HANDOFF.md` §13.1 有属性测试要求「context 存在与否不改变能力状态」。已定处置：`reduced` 档明确为「context 可用时的增强档」，缺 context 时降级为单档且不参与晋升判定。
- ~~导出是否包含 context 与图片~~ **已解决（2026-08-05，措辞 2026-08-07 更正）**：**概念上区分两种用途**——备份用途必须完整（events + contexts + 图片原始字节，才可称「备份」），交换用途不带 context / 图片（只能叫「抽象账本导出」，不得称为备份）。**当前只实现完整备份；抽象模式整体暂缓**（原因见 A1 切片 §3.1：`display` 携带原句，抽象包兑现不了"不含原文"的承诺）。原措辞"两种模式且命名有纪律"会被读成两种都已交付，故更正。

- **`focus` 落地是一次跨层同批升级，不是加个字段**（2026-08-07 登记）。启用 Coach 导入写账**之前**，下列全部必须同批完成，缺一不可：

  | 层 | 必须同批改的东西 |
  |---|---|
  | 存储 | `ContextRecord` 新增 `focus`；`contextHash` 输入纳入 `focus`；`contextsHaveSameIdentity` 纳入 `focus`（只进其一必然静默丢数据或永久保存失败） |
  | 身份 | `identityKey` 语义域从句级变为 chunk 级，须加命名空间前缀 |
  | 交换 | exchange exporter 的封闭字段表；`manifest.schemaVersion` **必须升版**（`focus` 改变 contextHash，即改变内容身份） |
  | 恢复 | restorer 的 context 校验与 hash 重算；L1–L3 往返等价；**旧包（无 `focus`）与新包的迁移测试** |

  **在这套升级完成之前，Coach 导入不得写账。** 否则会产出一批 `focus` 只存在于导入台账、不参与内容身份的条目，而它们的 hash 与后来的规则算出来不一样——同一条内容在升级前后是两个不同的 context，去重与恢复等价全部失效。
- **账本唯一权威设备 = iPhone 主屏 PWA，导入只在该设备发生**。在电脑上粘贴等于创建第二本正式账本（原 PRD 已将其列为明确后置），条目永远到不了手机而界面仍显示保存成功——这是最难自行发现的静默数据割裂。
- **v3 数据库升级是单向的**：IndexedDB 不能降版本。一旦某台设备升到 v3，回滚 web 包会在打开数据库时抛 VersionError 并使该设备的应用不可用，而当前完全没有 VersionError 兜底。部署须只前滚；功能开关须运行时可关且只关入口、不动已写数据；kill 的既定选择是「保留数据、只关入口」。注意：A1 恢复切片本身**不引入 DB v3**，见切片文档。
- **出向（截图与摘要贴给外部模型）发生在 Tenjin 之外**，原 PRD 12.2 的隐私前置（分析副本分离、去 EXIF/GPS、URL 清洗）在那里一条都无法由代码执行。它是纪律而非机制，须如实承认。实景照片（主机屏幕、纸面题目）可能带 GPS/EXIF；纪律是优先用截图而非拍照。

## 3. Stage 0（进行中，零代码）

用户已在其固定 Coach 会话中加入「整理」指令，Coach 已确认格式。Stage 0 只验证格式稳定性与用户意愿，**不要求把条目手工录入 Tenjin**（录入是后续要消灭的成本，在 Stage 0 做既费时间又不验证新东西）。仅抽取 5–8 条手工录入作为复习价值抽查。

### 3.1 计数口径（正式计数自本 rubric 冻结起开始）

**本 rubric 冻结之前已产生的样本不计入正式统计**，保留在本机作为解析器开发时的对照材料。入仓的解析 fixture 一律合成，真实样本只留本机（延续 `docs/learning/README.md` 的原文层边界）。

- **一次 attempt** = 一次**符合计数条件**的「整理」触发（计数条件见下方「连续五次遗忘」的分母定义：确实出现了值得整理的学习内容、且当时有条件触发）。一次 attempt 就是一个批次。
- **即使 Coach 输出无围栏、多围栏、围栏外有正文或非法 JSON，这次 attempt 仍然计入批次数**，并计为一次**格式失败**。这一条是关键：只统计"成功产出 JSON 的那些次"会让格式合格率永远偏高——失败的样本被从分母里悄悄拿掉了。
- `items` 为空的块是**正常输出**，同样算一个批次；它计入批次数，但不进入条目级统计的分母。
- 同一次 Coach 会话内多次触发「整理」记为多个 attempt。
- **Stage 0 全程由人依同一套规则判读，当前不存在任何运行中的 parser。** 判读用的规则就是 §2.2 与 §2.4；写下这条是因为"格式一次性可用"这个指标容易被误以为是某个程序跑出来的。
- **「愿意保留」按 item 统计**：分母 = 所有批次中的 item 总数；分子 = 用户会真正保留的 item 数。不按批次统计。
- **`transferSentence` 漂移率**：仅当带 `transferSentence` 的 item 累计 ≥10 条时才计算比率；不足则显示 `unavailable`，**不硬算 80%**（延续 `HANDOFF.md` §14.2「不以零代替缺失数据」）。**`unavailable` 是 non-blocking 的**——它不阻止 Stage 0 通过，但**Stage 1 一律不启用 transfer 档**（迁移句在 MVP-A 本来就只在采集端显式提供时才启用，见 §2.6）。这样"样本不够"不会变成一个悬而未决、既不通过也不否决的状态。
- **低产出的止损**：若累计 **10 次 eligible attempt 之后 item 总数仍 <5**，判定为**低产出并停止**，不进入 Stage 1。理由：`focus` 完整率与保留率都是**以 item 为分母**的比率，item 太少时它们没有分母、永远算不出来——若不设这条，Stage 0 会无限期停在"再攒攒"，既不通过也不失败。
- **「连续五次遗忘」的分母**：只计"确实出现了值得整理的学习内容、且当时有条件触发整理"的 Coach 会话。纯闲聊、无日语卡点、或会话被外部打断而无法触发的，不计入。

### 3.2 确定性提取顺序

顺序是**结构在先、内容在后**，且**结构检查不看内容**。这一点是本节的全部要害。

1. **数围栏总数**。整条回复的代码围栏数**必须恰好为 1**。为 0 或 ≥2 → 整批**格式失败**。
2. **检查围栏之外**。围栏以外的全部文本 `trim()` 后**必须为空**。有任何前言、后记、过渡句 → 整批格式失败。
3. **到这一步才碰内容**：对那唯一的围栏做 `JSON.parse`。失败 → 整批格式失败。
4. 严格 schema 校验（§2.2 的两层 `additionalProperties: false`）。
5. 字符串 trim 非空校验（§2.2）。
6. 任一步失败 → 整批拒绝，输出可回贴给 Coach 的重新输出指令。**不修复、不猜字段、不剥离未知键。**

**明确废除"先过滤非法围栏再数候选"的写法**（本节前一版就是那样写的，错了）。那种做法是：枚举全部围栏 → 跳过空的和 parse 失败的 → 看剩下几个"候选"。它的问题是**用内容去决定结构是否合法**：一条含两个围栏的回复，只要其中一个碰巧不是 JSON，就会被判成"恰好一个候选"而放行——而它明明违反了"围栏总数为 1"的合同。空围栏同理：真实样本里出现过的那个空围栏，在旧写法下被静默跳过，于是"回复里有两个围栏"这个事实从未被记录。

新写法把这条路堵死：**围栏数是纯结构量，先数，数完再谈内容**。代价是那个真实出现过的空围栏会让该批失败——这是**期望行为**，它说明 Coach 违反了合同，应当修 prompt 而不是让解析器替它兜着。

同样不做无围栏的括号配平扫描：正文里裸出现的 `{` 更可能是解释文字的一部分，扫它只制造假阳性。没给围栏就是契约违反。

### 3.3 判定阈值（预登记）

| 观察项 | 及格线 |
|---|---|
| 批次数 | ≥10 |
| 格式一次性可用（按 §3.2 提取 + schema 校验通过，无需手改） | ≥70% |
| `focus` 是可独立复习的最小完整 chunk（按 §2.1 定义，不以辞书形为准） | ≥80% |
| 给出 `transferSentence` 的条目中用法未漂移 | ≥80%，样本 <10 条时记 `unavailable` |
| 用户愿意真正保留的条目比例（按 item） | ≥50% |
| **错误内容被接受入账** | **0 容忍** |
| 用户是否真会触发「整理」 | 连续 5 次（按 §3.1 分母）遗忘或不愿触发即淘汰 |

**关于「0 容忍」的口径**：判定的是**有没有错的内容进了账**，不是 Coach 有没有输出过错的内容。而"错的内容"分两类，把关点完全不同：

| 类别 | 例子 | 谁能拦 | Stage 0 怎么处理 | Stage 1 怎么处理 |
|---|---|---|---|---|
| **结构错误** | 未知字段（★级评分、频率断言）、缺必填字段、非法 JSON、围栏数不对、围栏外有正文 | **parser** | 用户按 §3.2 的同一套规则人工判读，记为格式失败 | parser 整批失败 |
| **语义错误** | `answer` 是编造的、解释错了、`focus` 圈错 chunk、`sourceExcerpt` 与截图不符 | **只有人**。parser 完全无法识别 | 用户判读时拒绝该条 | **逐条预览时由用户拒绝**，该条不入账，记一次 prompt 缺陷 |

**必须删除的错误说法**：本节前一版写着"Coach 偶发输出编造的 answer…→ 该批被解析器整批拒绝（§2.2 未知键规则）"。**这是错的**，而且错得有害。`additionalProperties: false` 只拦**键名**；一个键名叫 `answer`、值是彻底胡编的字符串，schema 校验会**完全放行**。把编造内容算进 parser 的能力范围，会让人误以为"schema 过了 = 内容可信"——那正是这条路线最危险的误读。编造只能靠人在预览时拦。

**不因单次错误永久否决整条路线**：出现一次记一次 prompt 缺陷并修 prompt；只有同一类错误在修过 prompt 后仍反复出现（≥3 次）才判该项不合格。

Stage 0 的其余口径（每批 0–3 条、实际目标 1–2 条、全程零代码）**不因本次收口而改变**。

任何一项不及格，Coach 路停止，不进入实现阶段，且不发生任何工程投入。

**Stage 0 PASS 不自动授权 Stage 1。** 通过只意味着"这条路值得继续评估"，不意味着可以开工写导入器。Stage 1 必须**另立一份计划**、明确自己的文件写集、并**获得 owner 批准**——而且它还压着 §2.8 登记的 `focus` 跨层升级硬依赖：那套升级完成前，Coach 导入不得写账。

### 3.4 与 `explanation-policy.md` 的关系

本文档 §2.2 的普通模式合同（**逐句完整翻译**）相对 `explanation-policy.md` 的默认输出合同**具有优先级**，因为后者约束的是"解释输出什么"，而翻译不是解释。

具体对齐：`explanation-policy.md` §2「窄 focus」与 §7「默认输出合同」里的 1–3 个 focus 限制，**只约束追加讲解的广度**——即"哪些点值得展开"。它**不许可省略原文本身的逐句翻译**。该文件 §7 的"默认不输出"清单里列的是"与问题无关的逐词翻译"，指的是**逐词**对译，不是**逐句**通读翻译；两者被混淆过一次，在此写清。

若日后修订 `explanation-policy.md`，需同步这条，或在该文件里显式引用本节。

## 1. 决策内容

### 1.1 作废

《Tenjin Capture Inbox MVP PRD》（`docs/prd/2026-07-12-tenjin-capture-inbox-mvp.md`）的**近期实施范围**作废。逐条去留见该 PRD 文首批注——**按条款继承，不按整章继承**。

作废理由：该 PRD 的核心前提是「先收下、稍后理解」——用 iOS 分享菜单把文字/链接/截图批量投递到 iCloud，Tenjin 事后集中导入并处理。用户的真实行为与之相反：阅读中遇到卡点当场截图问外部 GPT Coach，即刻获得解释。因此该 PRD 的阶段门槛（阶段 B 的 10 次真实捕获 + 5 条延迟处理、阶段 C 的 50 次捕获 + 20 条延迟处理、第 16 章的完成定义）无法从用户的实际使用中产生数据，继续持有会让它变成一份既不能证实也不能证伪的僵尸计划，并与新方向争夺同一份稀缺资源（用户真实的日语阅读时间）。

### 1.2 采纳方向

**Coach 结构化剪贴板桥**：用户在外部 GPT Coach 会话末说「整理」，Coach 输出固定格式 JSON；Tenjin 提供粘贴导入、逐条预览确认后由本机生成事件。外部模型只能提议，用户确认才成为学习事实。

明确不做（升格为永不做）：后台定时抓取任何外部源；Coach 直连 Tenjin 的常驻推送链路（Custom GPT Action、公网服务端、鉴权队列）；Tenjin 内置视觉或 LLM API；画像自动同步或常驻上传；让导入成为记录的必经路径（无 LLM 的手动闭环必须永远完整可用）。

### 1.3 新增的一等设计约束：双硬门

用户明确指出：他真实的日语接触发生在三件他本来就在做的事里——看日文小说、玩日文游戏、刷日文社交内容；他不接受在这三件事之上再叠加一个「学习流程」。

这条约束的地位等同于 `HANDOFF.md` 的既有硬约束（不制造欠账、采集轻、最少维护），但**它不是"时间优先于学习效果"**。正确形式是两道硬门，必须同时成立才保留功能：

- **门① 时间受控**：额外 Tenjin 时间必须有明确预算。默认每周额外不超过**约 6 分钟**（不含他本来就在做的阅读与问 Coach）。随时可退出，不要求清空任何列表，不显示欠账或积压。
- **门② 价值可见**：在该预算内仍看不到回忆或迁移价值，就删除功能。**不能为了省时间而保留一个根本无效的工具。**

推论规则：任何增加单条目人工成本或复习次数的设计，必须先证明它在门①下仍成立；任何为省时间而削弱验证强度的设计，必须先证明它不会让门②失效。

### 1.4 关于用户的三个渠道（措辞受限）

**可以声称的**：在当前证据与维护预算下，唯一被真实行为验证、且能以低维护同时覆盖这三类场景的共同路径是「截图 → Coach」。

**不可声称的**：不说它是技术上唯一可能的路径——社交内容确有 API；小说若在支持选词复制的阅读器里也能直接取文本。这里成立的只是"在当前证据与维护预算下唯一成立的共同路径"，而不是"技术上唯一"。

**不可声称的**：不说"这三个渠道全部是阅读"。当前拟接入的卡点以阅读为主，因此 v1 先做 R；但游戏与视频同样可能产生听力卡点，只是当前不接。R 优先是范围选择，不是渠道性质的结论。

## 2. 已定的设计决策（供实现参考，细节待设计文档）

### 2.1 契约

`tenjin.coach-transfer/v1`，一批 0–3 条（实际入账目标 1–2 条，允许 0 条），v1 只做 R 项（`type: "lookup"`）。字段：

| JSON 键 | 落库位置 | 说明 |
|---|---|---|
| `focus` | 新增 `ContextRecord.focus`（可选） | 见下方定义。作为 `item_created` 的 `display` / `identityKey` 来源 |
| `sourceExcerpt` | 已有 `ContextRecord.original` | **不新增字段**，`original` 语义保持「采集到的原始文本」不变 |
| `answer` | 已有 `ContextRecord.answer` | 最多一两句 |
| `transferSentence` | 导入台账，**不进 ContextRecord** | 不进 contextHash、不进 identity 比较、不可作晋升证据 |

**`focus` 的定义**：可独立复习的最小完整 chunk；保留决定意义的助词、活用与句法槽位；**能规范化时才规范化，不强制辞书形**。若活用或语气本身就是要学的点（如 `〜ておけばよかった`、`〜てしまう`），保持该形态，不得强行还原成辞书形——强制辞书形会破坏 `explanation-policy.md` §3「chunk 必须保留必要的助词、补语或句法槽位；过度裁剪会造成错误泛化」。

L 通道不接（截图不能证明"没听出"，且现有 L 复习没有可核对锚点，批量导入 L 项会制造"无锚点却能产生验证证据"的题目）。P 通道只接真实的原表达 + 纠正版。

解析层必须剥离并向用户展示所剥离的内容：★级评分、频率与考级断言、词源理论、掌握程度判断。禁止把模型自评置信度当把关手段。

### 2.2 解析策略（已确认）

1. 提取顺序：先找带 `json` 标注的代码围栏；找不到再做括号配平扫描。详细的确定性顺序见 §3.2。
2. 严格 schema 校验：未知键、缺必填、类型错、schema 版本不符一律拒绝。
3. **不做智能修复、不猜字段。**
4. 出现多个能通过校验的候选块、或提取存在歧义时，**直接失败**并给出一段可回贴给 Coach 的重新输出指令。

### 2.3 必须同时满足的实现约束

- `focus` 必须**同时**进入 contextHash 输入与 `contextsHaveSameIdentity` 比较。只进其一必然导致静默丢数据或永久保存失败。
- contextHash 字段清单目前有三处副本，须合并为单点导出并加键集一致性测试；缺省字段继续整键省略，不得发 `null` 或空串（这是历史 hash 不变的唯一保证）。
- `identityKey` 语义域从句级变为 chunk 级，须加命名空间前缀（沿用既有 `image:` 先例）。
- 手动采集路径与导入路径第一天就统一为「`focus` 可选、缺省时从 `original` 派生」，不允许长出两类形状不同的 item。

### 2.4 复习与验证

- 间隔条件**只产生排序优先权，永不产生准入权**。未到期项不被剔除，只排在到期项之后。理由：硬门槛会让"到期集合"成为真实存在但界面不显示的量，即 `HANDOFF.md` 9.1 明文禁止的隐形欠账。
- 探测材料档位在 MVP-A 收敛为两档：`source`（来源句）→ `reduced`（focus 本身）。`transfer` 档仅在采集端显式提供迁移句时启用，未提供的项永远停在 `reduced` 且不受惩罚。
- `transfer` 档一律为**产出式探测**：题面 = focus + 「请自己造一句用到它的句子，或说出它适用什么场合」；生成内容只出现在揭示侧，永不进入被测面。
- 否决「至少一次 transfer 才能晋升 stable」：状态由事件重放派生，部署即让所有既有 stable 静默退回 unstable。替代为不进状态机的派生标记 `transferConfirmed`，仅用于展示与 stable 抽查排序。
- `probeSource` 须枚举化，且**必须保留 `"review"` 作为 legacy 值**，否则恢复等价验证会在校验历史事件时逐条失败。
- 复习默认改为**约 2 分钟的时间预算**（`HANDOFF.md` 9.1 承诺过但从未实现），不再显示"还剩几条"。
- 取消「必须凑满 20 个完整样本」这一指标目标。

### 2.5 完整状态备份必须覆盖什么（取代 REC-02 的字段清单）

**原则**：完整状态备份必须覆盖正式事件、contexts（含图片原始字节）、时钟与水位，以及**所有影响幂等与恢复正确性的 fold 外状态**——包括未来的 Coach 导入台账（import receipts）。

旧 PRD REC-02 列举的具体字段（Inbox 元数据、`sourceShardMonth`、`sourcePackageRelativePath`、`localDigestVersion`、`localPackageDigest`）绑定 Inbox 形态，不继承。继承的是"凡是不能由事件集重算、却影响幂等或恢复的状态，都必须进备份"这条原则。

A1 恢复切片的完整定义另见 [`2026-08-05-a1-ledger-recovery-slice.md`](2026-08-05-a1-ledger-recovery-slice.md)。

### 2.6 已知缺陷与未决项

- **导入幂等只在单设备成立**：导入台账不是事件、不能由事件集重算、不参与 `.tenjin` 交换。恢复到空库后重导同一批会静默重复；同一批 JSON 在两台设备各导一次会产生重复 item。这从设计上打破 `HANDOFF.md` §13.1 的属性「重复导入不增加证据」。处置：台账必须进备份与恢复等价校验（§2.5）；跨设备幂等作为已知缺陷纳入 A2。若 A0 最终决定批次身份进事件层，则台账实现需一次数据迁移。
- **探测材料档位依赖 context 是否存在**：默认导出不带 contexts，而 `HANDOFF.md` §13.1 有属性测试要求「context 存在与否不改变能力状态」。已定处置：`reduced` 档明确为「context 可用时的增强档」，缺 context 时降级为单档且不参与晋升判定。
- ~~导出是否包含 context 与图片~~ **已解决（2026-08-05）**：两种模式且命名有纪律——「完整备份」必须含 events + contexts + 图片原始字节；不含 context / 图片的只能叫「抽象账本导出」，不得称为备份。
- **账本唯一权威设备 = iPhone 主屏 PWA，导入只在该设备发生**。在电脑上粘贴等于创建第二本正式账本（原 PRD 已将其列为明确后置），条目永远到不了手机而界面仍显示保存成功——这是最难自行发现的静默数据割裂。
- **v3 数据库升级是单向的**：IndexedDB 不能降版本。一旦某台设备升到 v3，回滚 web 包会在打开数据库时抛 VersionError 并使该设备的应用不可用，而当前完全没有 VersionError 兜底。部署须只前滚；功能开关须运行时可关且只关入口、不动已写数据；kill 的既定选择是「保留数据、只关入口」。注意：A1 恢复切片本身**不引入 DB v3**，见切片文档。
- **出向（截图与摘要贴给外部模型）发生在 Tenjin 之外**，原 PRD 12.2 的隐私前置（分析副本分离、去 EXIF/GPS、URL 清洗）在那里一条都无法由代码执行。它是纪律而非机制，须如实承认。实景照片（主机屏幕、纸面题目）可能带 GPS/EXIF；纪律是优先用截图而非拍照。

## 3. Stage 0（进行中，零代码）

用户已在其固定 Coach 会话中加入「整理」指令，Coach 已确认格式。Stage 0 只验证格式稳定性与用户意愿，**不要求把条目手工录入 Tenjin**（录入是后续要消灭的成本，在 Stage 0 做既费时间又不验证新东西）。仅抽取 5–8 条手工录入作为复习价值抽查。

### 3.1 计数口径（正式计数自本 rubric 冻结起开始）

**本 rubric 冻结之前已产生的样本不计入正式统计**，保留在本机作为解析器开发时的对照材料。入仓的解析 fixture 一律合成，真实样本只留本机（延续 `docs/learning/README.md` 的原文层边界）。

- **一个批次** = 一次「整理」触发所产生的一个 JSON 块，`items` 为空的块同样算一个批次。同一次 Coach 会话内多次触发「整理」记为多个批次。空批次计入「批次数」，但不进入条目级统计的分母。
- **「愿意保留」按 item 统计**：分母 = 所有批次中的 item 总数；分子 = 用户会真正保留的 item 数。不按批次统计。
- **`transferSentence` 漂移率**：仅当带 `transferSentence` 的 item 累计 ≥10 条时才计算比率；不足则显示 `unavailable`，**不硬算 80%**（延续 `HANDOFF.md` §14.2「不以零代替缺失数据」）。
- **「连续五次遗忘」的分母**：只计"确实出现了值得整理的学习内容、且当时有条件触发整理"的 Coach 会话。纯闲聊、无日语卡点、或会话被外部打断而无法触发的，不计入。

### 3.2 确定性提取顺序

1. 在 Coach 本次回复中**自后向前**找最后一个带 `json` 语言标注的代码围栏；
2. 若无，自后向前找最后一个**非空**代码围栏（空围栏一律跳过，不作候选——首个真实样本就出现过正式 JSON 前的空围栏）；
3. 若仍无，从回复中最后一个 `{` 起做括号配平扫描，忽略字符串字面量内的括号；
4. 若第 1–3 步得到多于一个能通过 schema 校验的候选块，或提取过程存在歧义 → **整批失败**，输出可回贴给 Coach 的重新输出指令；
5. 得到唯一候选后做严格 schema 校验；任一项不合规 → 整批失败。不修复、不猜字段。

取"最后一个"而非"第一个"的理由：指令要求 JSON 附在正常回复**之后**，而正常回复正文里可能出现引用日文的围栏或示例。取最后一个是确定性的，且与指令一致。

### 3.3 判定阈值（预登记）

| 观察项 | 及格线 |
|---|---|
| 批次数 | ≥10 |
| 格式一次性可用（按 §3.2 提取 + schema 校验通过，无需手改） | ≥70% |
| `focus` 是可独立复习的最小完整 chunk（按 §2.1 定义，不以辞书形为准） | ≥80% |
| 给出 `transferSentence` 的条目中用法未漂移 | ≥80%，样本 <10 条时记 `unavailable` |
| 用户愿意真正保留的条目比例（按 item） | ≥50% |
| **错误内容被接受入账** | **0 容忍** |
| 用户是否真会触发「整理」 | 连续 5 次（按 §3.1 分母）遗忘或不愿触发即淘汰 |

**关于「0 容忍」的口径**：判定的是**有没有错的内容进了账**，不是 Coach 有没有输出过错的内容。Coach 偶发输出编造的 answer、★级评分或凭空频率断言 → 在核对时拒绝该条并修 prompt，记为一次 prompt 缺陷，**不因单次错误永久否决整条路线**。只有同一类错误在修过 prompt 后仍反复出现（≥3 次）才判该项不合格。

任何一项不及格，Coach 路停止，不进入实现阶段，且不发生任何工程投入。

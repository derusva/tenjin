# 切片定义：A1 账本导出 + 恢复 + 等价验证

**日期：** 2026-08-05（2026-08-07 修订，见 §9）

**状态：** 已冻结范围；导出器已合入 `fa4e048`。**恢复器：计划待审；批准后开工**（其中 CRC 路线须先由 owner 冻结，见计划 §3.3）

**性质：** 补 `HANDOFF.md` 阶段 A1 Gate 的既有欠债，**不是任何新功能的前置**

---

## 1. 为什么现在做

`HANDOFF.md` §12.2 阶段 A1 Gate 原文要求「`.tenjin` 完整包导出和恢复」，Gate 判据是「iPhone 主屏模式可离线完成 capture → item → review → export」。这条至今未实现：

- 数据页只有 5 行只读计数，零交互（`apps/web/src/App.tsx` data 视图）；
- `LedgerRepository` 接口只有 `reserveEventCoordinates` / `appendCapture` / `appendEvents` / `appendDiscard` / `readSnapshot` / `close`，**没有 export、import 或 delete**；
- 全应用唯一的纠错入口是 8 秒撤销 toast，最近记录只显示 3 条；超过 8 秒又滚出前 3 条的错误记录，界面上既不能编辑也不能删除。

也就是说：**账本目前没有任何备份或修复路径。** 在这个状态下开任何批量写入通道，坏一次就不可回滚。

因此本切片先做，且它**与 Coach 方向的成败无关**——不论 Coach 桥最终是否建成，账本都必须可恢复。

## 2. 范围

### 2.1 做

1. **导出**（✅ 已完成，`fa4e048`）：产出 `HANDOFF.md` §5.3 已定义的 `.tenjin` 包，不发明临时备份格式；仅完整备份模式。
2. **恢复**：**只**支持恢复到空账本。非空即拒，不做合并——原文的"至少支持"已作废，见 §5.2.1。
3. **等价验证**：一套能失败的验证器 + 负样本矩阵。
4. **数据页首次具备可操作入口**：导出、选择包恢复、以及恢复前的明确风险提示。
5. **真机走通一次完整往返**（见 §6）。

### 2.2 不做（本切片明确排除，避免范围蔓延）

- Coach 导入、粘贴解析、预览确认——等 Stage 0 判定；
- `focus` 字段与 contextHash 变更；
- **不升 DB 到 v3**（本切片不新增 object store，只读现有 events / contexts / clock）；
- 复习改造（时间预算、材料档位、间隔排序）；
- 增量包、跨设备合并、双 promote、redaction 执行、冲突收件箱；
- 恢复到**非空**账本（合并语义属 A2）。

## 3. 包格式（本切片：仅完整备份）

沿用 `HANDOFF.md` §5.3：

```text
manifest.json       schema 版本、ledger generation、导出设备、各 device 最大 seq
events.jsonl        当前持有的抽象事件
redactions.jsonl    无内容墓碑
contexts/           原文层；是否包含取决于模式
```

**本切片只有一种模式。**

| 模式 | 内容 | 允许的叫法 | 本切片是否交付 |
|---|---|---|---|
| 完整备份包 | events + contexts + **图片原始字节** + 时钟/水位 | 可以叫「备份」 | ✅ **唯一交付形态** |
| 抽象交换包 | 仅 events + 时钟/水位，不含 contexts 与图片 | 只能叫「抽象账本导出」，**界面不得称其为备份** | ⛔ **整体暂缓，见 §3.1** |

「暂缓」在本切片内是**彻底的**，不是"先做一半"：导出器不产出它（`LedgerPackageMode` 在 v1 是单成员字面量 `"full-backup"`，且 `buildManifest` 有运行时白名单），**恢复器必须拒绝任何 `mode !== "full-backup"` 的包**，界面不提供该选项，验收 Gate 里也不得出现依赖抽象包的断言。任何一处出现"两种模式"的措辞都是本文档的缺陷，不是可选项。

这与 `HANDOFF.md` §4.2「默认导出不带 contexts」不冲突：那条约束的是**交换**用途（另一台设备出现悬空 `context_hash` 是正常情况），而**备份**用途必须完整。两者是不同目的的两个模式；抽象模式恢复启用时再按上表分别命名并说明后果。

### 3.1 为什么抽象交换包暂缓（2026-08-05 修订）

抽象包唯一的存在理由是"不携带原文"。**按当前实现它做不到这一点**：`apps/web/src/features/capture/createCapture.ts:165` 把 `display = corrected ?? original` 写进 `item_created.payload.display`，而 lookup 类型下 `corrected` 恒为 `undefined`——于是整段粘贴的原文进了**事件本身**，而事件必然在抽象包里。这同时也违反 `HANDOFF.md` §4.1「事件只保留 `context_hash` 和必要的抽象学习字段；原句、人物、场合、URL 和媒体不进入状态字段」。

因此：**本切片只交付完整备份包。** 抽象交换包的前置条件是 `focus` 分离落地（`display` 从整句变成 chunk 级学习单元，见方向决策记录 §2.1、§2.3）。在那之前实现抽象模式，等于交付一个名字承诺了隐私、实际不成立的东西。

恢复抽象模式时的强制要求：泄漏断言的 fixture **必须包含真实的 `item_created` 事件**，不得只用 `capture_created`（其 payload 只有 `captureType`，扫描会真空通过）。

### 3.2 格式约束

- `redactions.jsonl` 目前必然为空（redaction 未实现）。manifest schema 必须**预留**该文件与相关字段，恢复器必须能接受它缺失或为空。
- `manifest.foldExternalState` 是**前向兼容闸，不是插槽**。一个空数组不能证明将来加入导入台账不破格式，所以不作此声称。它的语义是：**非空即表示该包携带了本版不认识的 fold 外状态，恢复器必须拒绝整个包**，而不是静默丢弃——静默丢弃正是「恢复看似成功、实则幂等信息已丢」的假绿。v1 导出恒为空数组；真正加入台账时**明确升 `schemaVersion` 到 2**，届时再冻结 descriptor 结构。现在不冻结，因为台账形状取决于 Stage 0 结果，提前设计就是提前造平台。

## 4. 恢复的硬要求

1. **全部校验在写入之前完成**：schema、包结构、`event_id` 唯一性、每设备 `seq` 单调、`occurred_at ≤ recorded_at`、事件与 context 交叉引用、图片摘要与字节一致、时钟/水位自洽。
2. **任何异常零写入**：失败时目标库逐字未变，不留半恢复状态。
3. **恢复后铸新 `device_id`**：`HANDOFF.md` §5.2「永不复用旧身份」。且本机 HLC 基线必须抬到已见最大值之上，下一次 `reserveEventCoordinates` 的 `seq` 从 1 起。
   - 这一条不是形式主义：`highWaterFromEvents` 在 clock 记录缺失时会从事件重建高水位；若复用旧 `device_id`，历史上被烧掉的 seq 空洞会被重新发放，而那些号可能已被别的副本用过 → 同 `eventId` 不同内容 → 交换时中毒，且延迟触发。

## 5. 验收 Gate

### 5.1 明确禁止的写法（否则会造出永远 PASS 的检查）

- ❌ `export(restore(export(D))) === export(D)` 定点等式作为 Gate——导出器少写一个字段时两侧同样少写，等式恒成立，是自证谎言；
- ❌ `JSON.stringify` 比对 context——两个内容完全不同的 Blob 都序列化成 `{}`，图片损坏永远发现不了；
- ❌ 只比对 `image.sha256` / `byteLength`——若恢复器自己重算摘要，损坏的字节会配上自洽的新摘要；必须**比字节**；
- ❌ 等价验证写死 store 名单——新增 store 会天然逃过比对，是随版本演进越来越空的检查；必须按 `db.objectStoreNames` **动态枚举**；
- ❌ 依赖框架 deep-equal 对 Blob 的语义——storage 测试跑 node 环境、web 测试跑 jsdom，语义随环境变化。

round-trip 与摘要比较**可以作为辅助断言**，但不得作为唯一 oracle。

### 5.2 六层验收

| 层 | 内容 |
|---|---|
| **L0 失败路径先证** | 喂一个中途截断的包，断言恢复抛错且目标库逐字未变（`HANDOFF.md` §5.4「导入中途被系统杀掉时，旧工作副本保持不变」） |
| **L1 存储级独立读取（分类穷尽）** | 绕开导出器，用 idb 直接对源库与恢复库按 `db.objectStoreNames` **动态枚举**。每个 store 必须落进下列两类之一，**未分类的 store 一律判失败**：<br>· **精确相等类**：`events`、`contexts`——复用 `structurallyEqual`（已含 Blob 逐字节、循环引用处理）比对，断言键集合相等 + 逐条相等 + 计数相等；<br>· **具名语义类**：`clock`——**不做逐条相等**，只按 L3 验证语义连续性（见下）。<br>「未分类即失败」是刻意的：将来新增的 store（首先会是导入台账）不能因为没人想起它而静默逃过比对，必须强制有人显式决定它属于哪一类。 |
| **L2 派生态等价** | `deriveLedger` 的 `ItemView` 逐字段相等（含 `channels` / `validPassDates` / `atRiskSince` / `lastFailureAt`）；`buildReviewQueue` 在同预算下产出相同的 `(itemId, channel, prompt, reveal)` 序列。（抽象交换包的对应断言——R/L/P 状态一字不变、复习队列缩减到写死的确定条数——随该模式一并暂缓，见 §3.1。） |
| **L3 身份与时钟连续性** | **全部只读**，验证器不得改动被验证的库：① `global-hlc` 已持久化且严格大于包内最大 `hlc`；② 包内每个历史设备的 `device-sequence` 水位已持久化且值正确；③ 新 `device_id` 在首次 reserve 之前**不存在** `device-sequence` 记录。「首次 `reserveEventCoordinates` 返回 `seq === 1`」必须在**一次性克隆库**上验证——在正式恢复库上调用它会写 clock、污染刚恢复的账本，让验证行为本身改变被验证对象。`clock` store 被清空必须产生**专属的 `L3_CLOCK`** failure，不得只表现为泛化的"某处不等"。 |
| **L4 重复恢复语义** | 见 §5.2.1。**泄漏 Gate 随抽象模式一并暂缓**：本切片不产出抽象包，因此不存在"不含原文"这个负向结论可证；完整备份本就应当携带全部原文，对它做泄漏断言是无意义的。导出器已建好扫描器并用**正向对照**证明它确实能看穿 zip（`packages/exchange/src/inspectPackage.ts`），抽象模式恢复时直接启用，不需要重建。 |
| **L5 会失败的证明** | 见下方负样本矩阵；每个负样本都**必须**让验证器非零退出 |

### 5.2.1 「同一包连续恢复两次」的冻结语义（2026-08-07）

原文写的是「同一包连续恢复两次结果不变」。这句话有歧义，且最坏的读法会**诱导实现出非空库合并**——而合并语义属于 A2，本切片明确不做。因此冻结为四条，缺一不可：

1. **第一次恢复到空库成功**；
2. **第二次必须被拒绝**，理由是目标库非空——不是"幂等地重放一遍"，也不是"检测到相同内容所以跳过"；
3. **拒绝之后，数据库逐条记录与逐字节不变**（按 L1 的分类穷尽口径比对，第一次恢复后的快照 vs 第二次被拒后的快照）；
4. **不得为满足本条而实现任何非空库合并、去重或覆盖路径**。恢复器只有"空库"一条入口；非空即拒。

第 2 条之所以要写死"因为非空而拒"，是因为"检测到内容相同所以跳过"看起来同样能让测试变绿，却悄悄引入了一条内容比对的合并前身，日后极易演化成半个 merge。

### 5.3 负样本矩阵（每条都必须能红）

| # | 变异 | 覆盖的不变量 |
|---|---|---|
| 1 | 删掉某 context 的 `answer` 键 | 丢字段 |
| 2 | 改某事件的 `recordedAt` 1 毫秒 | 改事件 |
| 3 | 图片 Blob 少一字节但重算 `sha256` 使其自洽 | 损坏 Blob（且专打"只比摘要"这种假绿） |
| 4 | 200 条事件删 1 条 | 事件数量 |
| 5 | 包被截断 | 截断包 |
| 6 | manifest 写未知 schema 版本 | 未知版本 |
| 7 | 重复 `eventId` 但内容不同 | 冲突 eventId |
| 8 | 清空 clock store | 时钟/水位损坏 |
| 9 | 篡改 manifest 的各 device 最大 seq | 水位自洽 |
| 10 | 恢复后 `clock` 的 global-hlc 低于包内最大 hlc | L3 语义连续性（取代原「抽象包混入原文」一条，后者随抽象模式暂缓） |
| 11 | 篡改 `events.jsonl` / `manifest.json` 的**压缩数据**、不更新 CRC，且解压后仍是合法 UTF-8 / JSON / 通过 schema | ZIP 完整性（`CRC_MISMATCH`）。这是唯一能证明"CRC 校验真的在跑"的测试——其余全部校验对它无感，因为它构造成处处合法。**依赖计划 §3.3 的 CRC 路线冻结** |

伪造 `originalSize` 的 zip bomb **保留为解包器单测**（不占矩阵编号）但必须存在：它与第 11 条守的是两件不同的事——前者是**体积**，后者是**完整性**。

**关于泄漏扫描器**（本切片不使用，记录其纪律供抽象模式恢复时套用）：扫描必须**先解压全部条目再扫描解压后的内容**。直接扫描 zip 字节是无效断言——包是 deflate 压缩的，明文本来就搜不到，那样的检查即使数据确实在包里也会通过。扫描器本身必须先用**正向对照**证明它有效（对完整备份断言哨兵串**确实能被找到**），再用于证明任何"不含原文"的负向结论。导出器已按此建成并通过正向对照。

外加两条 **must-not-fail** 用例，必须仍然 PASS——防止验证器过敏到只能靠字节巧合通过：

- `events.jsonl` 行序打乱；
- JSON 对象键序打乱。

## 6. 真机 runbook（切片的最终 Gate）

在真实 iPhone 主屏 PWA 上完成一次：**完整备份 → 清空测试账本 → 恢复 → 继续记录和复习**。

⚠️ **必须用测试账本，不得用真实账本。** 清空的机制是删除主屏图标（`HANDOFF.md` §11.6：删除主屏图标会删除本机工作副本），这是**不可逆**的。若确实只有一个真实账本可用，则必须先在桌面环境用同一个备份包完成一次成功恢复并通过 L1–L3，才允许在真机上清空。

同时记录：飞行模式下能否导出、包体积、恢复耗时、以及恢复后能否继续正常采集与复习。

## 7. 切片顺序（每步自带 Gate，不过就停在那里）

1. **导出器**（✅ 已完成，合入 `fa4e048`）：canonical 排序 + manifest + **仅完整备份**。Gate：产出包能被独立脚本解析；泄漏扫描器建成并通过正向对照。
2. **恢复器**：解析 → 全量校验 → 写入空库 → 铸新 `device_id` → 抬 HLC 基线。Gate：L0 截断包失败后旧库逐字未变。
3. **等价验证器 + 负样本矩阵**：Gate：10 条负样本全部能红 + 2 条 must-not-fail 仍绿。
4. **数据页可操作入口**：导出、恢复、风险提示文案。Gate：界面明确说明这是**完整备份**、包含全部原文与图片原始字节，以及恢复只能写入空账本。**本切片没有第二种模式可供命名。**
5. **真机往返**：Gate：§6 全过。

### 7.1 交付口径：UI 完成前只能称 BACKEND_READY（2026-08-07）

第 2、3 步完成后**不得**声称"端到端恢复已交付"或"A1 Gate 已过"。恢复能力要真正可用，依赖第 4 步 UI 落地的六步激活协议（禁写 → 写并读回 `pendingRestoreDeviceId` → restore → 提升为 `tenjin.deviceId` → 关闭 repository → reload），因为 `deviceId` 存在 localStorage、时钟存在 IndexedDB，是两个独立存储；只写对其中一个就会出现"新账本配旧身份"。

在第 4 步完成之前，正确的说法是 **BACKEND_READY**：恢复能力在后端可用并已验证，用户尚不能完成一次真实恢复。

### 7.2 关于"零写入风险"的措辞更正（2026-08-07）

本节原文写「前三步对现有数据零写入风险，可以先做完再碰 UI」。**这句话是错的，已作废。**

只有第 1 步（导出器）是纯读取，对现有数据零写入风险。**第 2 步恢复器是本项目历史上第一个真正的写库能力**：在它之前，`LedgerRepository` 只有单条 `appendCapture` / `appendEvents` / `appendDiscard`，没有任何能一次性写入整个账本的路径。恢复器新增的是"一个事务写入全部 events + contexts + clock"这种量级完全不同的能力，风险面与前一步不可同日而语。

因此第 2、3 步的排序理由必须重述为：**先建验证器再放量，而不是"反正没风险"**。具体纪律见 §4 的三条硬要求，以及计划文档里"事务内不得 await 非 IndexedDB Promise""空库检查必须在最终写事务内复检"两条。

## 8. 与其他工作的关系

- **独立于** Coach 导入、`focus` 字段、DB v3、复习改造。这四项都不在本切片内。
- 本切片完成后，账本才第一次真正可恢复；之后再决定往里面增加什么。
- 未来的 fold 外状态（导入台账）由 `manifest.foldExternalState` 这道**前向兼容闸**看守，不是"插槽"：v1 导出恒为空数组，**恢复器遇到非空一律拒绝整个包**。空数组不构成任何前向兼容承诺；真加台账时明确升 `schemaVersion` 到 2 并届时冻结结构（见 §3.2）。

### 9.1 v1.2 推翻了哪些旧判断，以及为什么

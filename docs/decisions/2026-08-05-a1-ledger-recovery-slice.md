# 切片定义：A1 账本导出 + 恢复 + 等价验证

**日期：** 2026-08-05

**状态：** 已冻结范围，可立即开工

**性质：** 补 `HANDOFF.md` 阶段 A1 Gate 的既有欠债，**不是任何新功能的前置**

---

## 1. 为什么现在做

`HANDOFF.md` §12.2 阶段 A1 Gate 原文要求「`.tenjin` 完整包导出和恢复」，Gate 判据是「iPhone 主屏模式可离线完成 capture → item → review → export」。这条至今未实现：

- 数据页只有 5 行只读计数，零交互（`apps/web/src/App.tsx` data 视图）；
- `LedgerRepository` 接口只有 `reserveEventCoordinates` / `appendCapture` / `appendEvents` / `appendDiscard` / `readSnapshot` / `close`，**没有 export、import 或 delete**；
- 全应用唯一的纠错入口是 8 秒撤销 toast，最近记录只显示 3 条；超过 8 秒又滚出前 3 条的错误记录，界面上既不能编辑也不能删除。

也就是说：**账本目前没有任何备份或修复路径。** 在这个状态下开任何批量写入通道，坏一次就不可回滚。

因此本切片先做，且它**与 Coach 方向的成败无关**——不论 Coach 桥最终是否建成，账本都必须可恢复。

## 2. 范围

### 2.1 做

1. **导出**：产出 `HANDOFF.md` §5.3 已定义的 `.tenjin` 包，不发明临时备份格式。
2. **恢复**：至少支持恢复到**空账本**。
3. **等价验证**：一套能失败的验证器 + 负样本矩阵。
4. **数据页首次具备可操作入口**：导出、选择包恢复、以及恢复前的明确风险提示。
5. **真机走通一次完整往返**（见 §6）。

### 2.2 不做（本切片明确排除，避免范围蔓延）

- Coach 导入、粘贴解析、预览确认——等 Stage 0 判定；
- `focus` 字段与 contextHash 变更；
- **不升 DB 到 v3**（本切片不新增 object store，只读现有 events / contexts / clock）；
- 复习改造（时间预算、材料档位、间隔排序）；
- 增量包、跨设备合并、双 promote、redaction 执行、冲突收件箱；
- 恢复到**非空**账本（合并语义属 A2）。

## 3. 包格式与两种模式

沿用 `HANDOFF.md` §5.3：

```text
manifest.json       schema 版本、ledger generation、导出设备、各 device 最大 seq
events.jsonl        当前持有的抽象事件
redactions.jsonl    无内容墓碑
contexts/           原文层；是否包含取决于模式
```

**两种模式，命名必须有纪律：**

| 模式 | 内容 | 允许的叫法 |
|---|---|---|
| 完整备份包 | events + contexts + **图片原始字节** + 时钟/水位 | 可以叫「备份」 |
| 抽象交换包 | 仅 events + 时钟/水位，不含 contexts 与图片 | 只能叫「抽象账本导出」，**界面不得称其为备份** |

这与 `HANDOFF.md` §4.2「默认导出不带 contexts」不冲突：那条约束的是**交换**用途（另一台设备出现悬空 `context_hash` 是正常情况），而**备份**用途必须完整。两者是不同目的的两个模式，界面上必须分别命名并说明后果。

两项格式约束：

- `redactions.jsonl` 目前必然为空（redaction 未实现）。manifest schema 必须**预留**该文件与相关字段，恢复器必须能接受它缺失或为空。
- manifest 必须可扩展地承载未来的 fold 外状态（首先是 Coach 导入台账，见方向决策记录 §2.5），使将来加入它时不构成格式破坏。本切片只**预留插槽**，不实现台账。

## 4. 恢复的硬要求

1. **全部校验在写入之前完成**：schema、包结构、`event_id` 唯一性、每设备 `seq` 单调、`occurred_at ≤ recorded_at`、事件与 context 交叉引用、图片摘要与字节一致、时钟/水位自洽。
2. **任何异常零写入**：失败时目标库逐字未变，不留半恢复状态。
3. **恢复后铸新 `device_id`**：`HANDOFF.md` §5.2「永不复用旧身份」。且本机 HLC 基线必须抬到已见最大值之上，下一次 `reserveEventCoordinates` 的 `seq` 从 1 起。
   - 这一条不是形式主义：`highWaterFromEvents` 在 clock 记录缺失时会从事件重建高水位；若复用旧 `device_id`，历史上被烧掉的 seq 空洞会被重新发放，而那些号可能已被别的副本用过 → 同 `eventId` 不同内容 → 交换时中毒，且延迟触发。

## 5. 验收 Gate

### 5.1 明确禁止的写法（否则会造出永远 PASS 的检查）

- ❌ `export(restore(export(D))) === export(D)` 定点等式作为 Gate——导出器少写一个字段时两侧同样少写，等式恒成立，是自证谎言；
- ❌ `JSON.stringify` 比对 context——两个内容完全不同的 Blob 都序列化成 `{}`，图片损坏永远发现不了；
- ❌ 只比对 `image.sha256` / `byteLength`——若恢复器自己重算摘要，损坏的字节会配上自洽的新摘要；必须**比字节**；
- ❌ 等价验证写死 store 名单——新增 store 会天然逃过比对，是随版本演进越来越空的检查；必须按 `db.objectStoreNames` **动态枚举**；
- ❌ 依赖框架 deep-equal 对 Blob 的语义——storage 测试跑 node 环境、web 测试跑 jsdom，语义随环境变化。

round-trip 与摘要比较**可以作为辅助断言**，但不得作为唯一 oracle。

### 5.2 六层验收

| 层 | 内容 |
|---|---|
| **L0 失败路径先证** | 喂一个中途截断的包，断言恢复抛错且目标库逐字未变（`HANDOFF.md` §5.4「导入中途被系统杀掉时，旧工作副本保持不变」） |
| **L1 存储级独立读取** | 绕开导出器，用 idb 直接对源库与恢复库按 `db.objectStoreNames` 动态枚举逐 store `getAll`，复用仓内已有的 `structurallyEqual`（已含 Blob 逐字节、循环引用处理）比对；断言 store 键集合相等 + 逐条相等 + 计数相等 |
| **L2 派生态等价** | `deriveLedger` 的 `ItemView` 逐字段相等（含 `channels` / `validPassDates` / `atRiskSince` / `lastFailureAt`）；`buildReviewQueue` 在同预算下产出相同的 `(itemId, channel, prompt, reveal)` 序列。抽象交换包模式下必须断言 R/L/P 状态**一字不变**（`HANDOFF.md` §13.1「context 存在与否不改变能力状态」），且复习队列缩减到一个**写死的确定条数**，不许写成 `>= 0` |
| **L3 分配器连续性** | 恢复后首次 `reserveEventCoordinates` 使用新 `device_id`、`seq` 从 1 起、`hlc` 严格大于全部导入事件的最大 `hlc` |
| **L4 泄漏与幂等** | 抽象交换包的原始字节里不得出现任何 `context.original` / `answer` 的子串（哨兵串测试，`HANDOFF.md` §13.3「导出包不意外携带原文」）；同一包连续恢复两次结果不变 |
| **L5 会失败的证明** | 见下方负样本矩阵；每个负样本都**必须**让验证器非零退出 |

### 5.3 负样本矩阵（每条都必须能红）

| # | 变异 | 覆盖的不变量 |
|---|---|---|
| 1 | 删掉某 context 的 `answer` 键 | 丢字段 |
| 2 | 改某事件的 `recordedAt` 1 毫秒 | 改事件 |
| 3 | 图片 Blob 少一字节但重算 `sha256` 使其自洽 | 损坏 Blob（且专打"只比摘要"这种假绿） |
| 4 | 200 条事件删 1 条 | 事件数量 |
| 5 | 包被截断 | 截断包 |
| 6 | manifest 写未知 schema 版本 | 未知版本 |
| 7 | 重复 `eventId` 但内容不同 | 冲突 eventId |
| 8 | 清空 clock store | 时钟/水位损坏 |
| 9 | 篡改 manifest 的各 device 最大 seq | 水位自洽 |
| 10 | 抽象交换包里混入原文 | 泄漏 |

外加两条 **must-not-fail** 用例，必须仍然 PASS——防止验证器过敏到只能靠字节巧合通过：

- `events.jsonl` 行序打乱；
- JSON 对象键序打乱。

## 6. 真机 runbook（切片的最终 Gate）

在真实 iPhone 主屏 PWA 上完成一次：**完整备份 → 清空测试账本 → 恢复 → 继续记录和复习**。

⚠️ **必须用测试账本，不得用真实账本。** 清空的机制是删除主屏图标（`HANDOFF.md` §11.6：删除主屏图标会删除本机工作副本），这是**不可逆**的。若确实只有一个真实账本可用，则必须先在桌面环境用同一个备份包完成一次成功恢复并通过 L1–L3，才允许在真机上清空。

同时记录：飞行模式下能否导出、包体积、恢复耗时、以及恢复后能否继续正常采集与复习。

## 7. 切片顺序（每步自带 Gate，不过就停在那里）

1. **导出器**：canonical 排序 + manifest + 两种模式。Gate：产出包能被独立脚本解析，抽象包通过哨兵串泄漏断言。
2. **恢复器**：解析 → 全量校验 → 写入空库 → 铸新 `device_id` → 抬 HLC 基线。Gate：L0 截断包失败后旧库逐字未变。
3. **等价验证器 + 负样本矩阵**：Gate：10 条负样本全部能红 + 2 条 must-not-fail 仍绿。
4. **数据页可操作入口**：导出、恢复、风险提示文案。Gate：界面对两种模式分别命名，抽象模式明确标注"不是备份"。
5. **真机往返**：Gate：§6 全过。

前三步对现有数据零写入风险，可以先做完再碰 UI。

## 8. 与其他工作的关系

- **独立于** Coach 导入、`focus` 字段、DB v3、复习改造。这四项都不在本切片内。
- 本切片完成后，账本才第一次真正可恢复；之后再决定往里面增加什么。

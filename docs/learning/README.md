# Tenjin Learning 文档边界

本目录用于承接“如何根据个人学习证据决定解释什么、跳过什么，以及哪些能力值得进入产品验证”的文档。它不是新的学习状态事实源，也不修改 Tenjin 既有的 R（阅读识别）/ L（听力识别）/ P（产出调用）状态机。

## 四层权威

四层先按适用范围划界，再谈优先级。系统状态、产品合同、个性化偏好和产品假设不能互相越权。

| 层级 | 权威与来源 | 可以决定 | 不能决定 |
|---|---|---|---|
| L1 运行事实层 | 正式事件账本、已接受/撤销的用户决策、当前代码与测试 | 对某个 item 而言，事件账本及其确定性派生决定当前 R/L/P 状态；代码与测试决定运行行为及某能力是否已经交付 | 不能因为实现暂时缺失就改写产品合同；根 `README.md` 只是当前使用摘要，发生漂移时应回查代码与测试 |
| L2 产品合同层 | 根 `HANDOFF.md`；本目录的 `explanation-policy.md` | `HANDOFF.md` 定义架构、事件、隐私、proposal 和 R/L/P 边界；解释策略只定义输出选择与呈现 | 解释策略不得创建能力事实、覆盖状态机或绕过 proposal 接受门 |
| L3 本地用户证据层 | `learner-profile.local.md` 中带状态、时间和来源的条目 | `user-confirmed` 条目可调整解释焦点、深度和默认 skip；用户本轮的明确要求优先于旧画像 | 不得直接改 R/L/P；`GPT-inferred` 和 `hypothesis` 不得触发抑制、晋升或不可逆决定 |
| L4 候选输入层 | 外部学习诊断稿、`product-hypotheses.md`、模型生成建议 | 形成待验证问题、proposal、实验和 Gate | 不是已确认画像，不是已交付功能，也不能作为用户能力或产品状态的直接证据 |

冲突处理规则：

1. 先判断冲突属于哪个决策域。产品状态看 L1，架构语义看 L2，解释偏好看用户当前明确要求和 L3。
2. 当前明确提问会绕过历史 `stable` / `suppressed` 的默认静默规则，但不会因此改变 R/L/P 状态。
3. 代码与文档不一致时，将其记录为实现或文档漂移；不能借此把候选能力描述成已交付。
4. `HANDOFF.md` 与本目录文档冲突时，以 `HANDOFF.md` 的事件、状态、隐私和 proposal 边界为准。
5. 模型推断与用户明确反馈冲突时，保留来源记录并以较新的明确反馈为准；推断不得静默升级为事实。

## 来源边界

- 根 `HANDOFF.md` 是 Tenjin 产品设计与架构合同；本目录不复制或重定义其事件状态机。
- 根 `README.md` 是已交付使用面的导航摘要；“当前可用”仍需由代码、测试或运行证据确认。
- `learner-profile.local.md` 是唯一允许保存具体个人学习细节的本目录文件。根 `.gitignore` 强制忽略 `docs/learning/*.local.md`；该文件可单独删除，且删除后不得破坏正式事件账本、查询或复习。
- 外部学习诊断稿是导入证据，不是权威数据库。只有明确归因且可追溯的内容才能进入本地画像；推断必须保留推断标签。
- `explanation-policy.md` 只保存可复用的解释规则，不复制个人成绩、个人目标、具体薄弱项或个人历史例子。
- `product-hypotheses.md` 只保存通用产品假设、依赖和验收 Gate，不复制个人画像内容。
- 原句、人物、场合、URL 等 context 继续遵守 `HANDOFF.md` 的独立原文层边界，不进入热画像或通用策略文档。

## 更新纪律

- 新增个人画像条目时必须同时写 `status`、`observed_at` 和 `source`。
- 只有用户直接陈述或明确接受的内容可标为 `user-confirmed`。
- 模型从对话、成绩或行为推导出的结论一律标为 `GPT-inferred`。
- 尚未验证的学习方法、因果解释或产品判断一律标为 `hypothesis`。
- 自由文本反馈若需要模型解释，先生成 proposal；用户接受后才可形成 `user-confirmed` 条目。
- 不把本地画像复制进通用文档、issue、测试 fixture 或日志。远端模型默认不得接收画像；只有用户显式触发、预览并确认后，才可发送当前任务所需的最小、已裁剪片段，且不得形成远端事实源。
